# ADR-0006: PWA como forma de entrega

- Status: **Proposto**
- Data: 2026-10-26

## Context

O produto precisa ser instalável em desktop e celular, usado diariamente, com notificações push e uma visualização 3D. Não há requisito de acesso a APIs nativas além de notificações. Equipe pequena: manter uma única base de código é relevante. O cliente fala com a API same-origin (ADR-0003).

## Decision

1. **PWA** com React + TypeScript + Vite + `vite-plugin-pwa` (Workbox, estratégia `injectManifest` para controlar o SW de push), manifest completo e ícones maskable.
2. **Service Worker** com: precache do *app shell* e assets versionados com hash; handlers de `push`/`notificationclick`/`pushsubscriptionchange`; **sem cache de respostas autenticadas da API** por padrão; atualização com *prompt* ao usuário.
3. **Offline na v1** = abrir o shell e mostrar último estado de telas explicitamente cacheáveis (somente leitura). **Escrita offline fica fora** (D-07); `Idempotency-Key` já deixa o caminho aberto.
4. **Push é do servidor** (ADR-0004); o cliente só inscreve (após gesto do usuário) e exibe. Guiar instalação no iOS (necessária para push).
5. **3D** (Three.js/R3F/Drei) em *chunk* carregado sob demanda, desacoplado das features (consome view-models), com **fallback 2D**, respeito a `prefers-reduced-motion` e orçamento de desempenho; toda função é acessível sem o 3D.
6. Cliente de API **gerado do OpenAPI**; compatibilidade aditiva na v1 para tolerar SW/clients desatualizados.
7. Logout limpa caches, estado local e remove a push subscription do dispositivo.
8. Qualidade medida por Lighthouse CI (installable, performance, a11y) e E2E.

## Alternatives considered

1. **App nativo (iOS/Android) / React Native / Flutter**: melhor integração e push nativo, mas múltiplas bases/lojas/custos; não solicitado. Rejeitado agora.
2. **Capacitor/Tauri/Electron envolvendo a web app**: viável como evolução se limitações de plataforma (ex.: push no iOS) se mostrarem bloqueantes; reaproveita a SPA.
3. **SPA sem PWA** (somente site): sem instalação/push confiável; não atende o requisito.
4. **SSR/Next.js**: ganhos de SEO inexistentes (app autenticado); adiciona runtime Node; rejeitado.
5. **Offline-first completo (sincronização, CRDT/IndexedDB)**: grande complexidade e conflitos; sem requisito; adiado (D-07).
6. **Blazor WASM**: uniria C# no front, mas o enunciado fixa React/TS e o ecossistema R3F.

## Consequences

**Positivas**: uma base de código para desktop e celular; instalação sem loja; atualização imediata; reaproveita API e auth same-origin; push padrão da web.

**Negativas / custos**: limitações de plataforma (push no iOS só instalada; economia de bateria; navegadores com políticas distintas); service worker é fonte clássica de bugs de cache/versão — exige testes e política de atualização cuidadosa; 3D aumenta bundle e consumo de bateria em celulares (mitigado por lazy-load, orçamento e fallback); sem escrita offline na v1; dependência de WebGL no dispositivo.
